# 小说工作台入口

项目仍是项目；本 skill 只编排准备、打开、等待与交接。引擎在仓库 `shared/`，小说的配置、素材、正文与进度保留在各自目录。页面 ready 不是执行授权。

## 准备当前任务

1. 从本文件 `skills/novel-studio/SKILL.md` 向上两级定位仓库根目录，核实 `shared/launch_studio.py` 存在；不要假定当前工作目录就是仓库。解析用户给出的小说路径、工作流与章节；已提供的信息不要重复问。
2. 已有项目先读取当前 graph.yaml、pipeline.json 和任务所需素材。保留现有配置和历史进度，仅按用户任务调整本项目的节点、提示词、skills、依赖及参数；不要重写 WebUI。只有明确新建小说时才按 novel-runner 的初始化流程创建目录，不覆盖现有项目。
3. 让启动器做只读 DAG 校验。准备阶段不要调用 `pipeline.py status`（会写状态），更不要 `reconcile`、`start`、`run`、人工放行或生成正文。模型由感知到的宿主及 `subagents/manifest.json` 解析；不要在这里新增模型覆写或擅改宿主注册文件。

## 打开并等候真实渲染

使用当前可用 Python 运行稳定启动器。以下是在仓库根目录的示例；其他目录下把脚本换成已核实的绝对路径：

```bash
python shared/launch_studio.py --project "D:/桃园密码" --workflow graph.yaml --chapter 51
```

省略 `--chapter` 时沿用图中章节。启动器会核对完整身份：同项目、同工作流和同章节的实例可复用，其他实例换端口；不要只看 health 200 或 slug，不要杀已有服务。

若需要宿主浏览器工具打开，使用 `--no-open` 并在后台运行启动器；读取 stderr 中本次 URL，用浏览器工具访问该 URL。`--no-open` 仍然等待真实页面回执，不是绕过就绪检查。用有上限的 `--timeout` 留出操作时间。不要读取整份宿主工具日志来找 URL。

只认可本次启动器退出码 0，且 stdout JSON 的 `status` 为 `ready`、`awaiting_confirmation` 为 true。它已校验本次 `launch_id` 和工作流 revision；旧标签页、壳页面、health 200、启动命令已发出都不算就绪。不要由宿主手工 POST `/api/ui/ready` 冒充浏览器完成渲染。

超时、坏图、浏览器拒绝打开或版本变化时，如实报告未就绪，修复后重新启动获得新回执；不能继续执行。

## 主对话交接

就绪后由 supervisor 在主对话给出本次工作台 URL、小说与章节，并问：

> 工作流已加载，可以先调整节点提示词和技能并保存。现在可以开始跑工作流了吗？

到此结束本轮回复，等待用户明确答复。不要增加 WebUI 运行按钮，也不要把准备任务的“开始吧”、自动工具通知或页面回执当成此轮执行批准。

收到明确批准后，重新读取用户已保存的 graph.yaml 和当前状态，再按需读取仓库 `skills/novel-runner/SKILL.md` 执行。若存在未保存编辑，先请用户保存；若项目、章节或执行范围已经改变，说明新范围并重新确认。人工审核节点仍需各自的人工确认；本次启动批准不能一并放行所有人工门。

本轮入口仅支持当前单章或现有卷工作流；不要宣称已有第51–60章的外层十节点下钻图，也不要用同一章图并发覆盖多章。
